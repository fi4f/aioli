Contributing

Small modules. Readable changes.

The editor is Lisp source; JavaScript supplies the browser services it needs. Choose the smallest layer that can express your change.

Run locally

npm ci
npm start

Open the workshop and these docs. Node.js 20 or later is sufficient. The application has no browser package dependencies; Prettier is a development tool for consistent source formatting.

Where to make a change

Change Start here
Editor layout or actions editor/workspace.lisp and individual files in editor/
Widgets, controls, source painting editor/ui/buttons.lisp, editor/ui/sliders.lisp, editor/ui/code-input.lisp
Source input, caret/selection data code-input.js
Highlighting incomplete source source-tokens.js
Language forms or CPU functions lisp.js
Shader expressions or commands shader.js
Drawing primitives and clipping drawing.js
WebGPU bindings and uploads gpu.js
Procedural synthesis audio.js
Browser bindings, saving, evaluation app.js
User documentation Static HTML files in docs/
Current project validation and private application namespaces project.js
Default generator and command source editor/policy/ and editor/templates/

There is no JavaScript evaluation of user source. The strict Lisp reader handles evaluation; the lossless display scanner handles incomplete text. Keep those responsibilities separate. A parser error must not prevent source from being visible.

Editor module layout

editor/ui/components.lisp imports reusable controls from editor/ui/, while main.lisp imports editor/workspace.lisp. The workspace composes code, files, game and parameter panes plus menu, generator, palette and preview widgets. Theme and state defaults live in editor/state.lisp. Each file owns its component's drawing and interaction; browser decoding lives in asset-preview.js and tab fitting/workflows live in editor/policy/. code-tabs.js caches and applies Lisp results.

To add a bundled Lisp module, create its file, import it from the appropriate Lisp entry or component, and add its path to editor-sources.js. The manifest loads the initial project and recovery sources over static URLs. Project-local imports then use editable source buffers, not additional network fetches. Save/Open includes every module; custom components are preserved. Use latest editor backs up modified components beside their originals before installing bundled versions, preserving relative import resolution.

Source buffers use LF newlines, matching the browser textarea. Bundled sources, imported Lisp files, project loads and saves normalize CRLF and lone CR. Git attributes keep checked-out text files on LF too. source-text.js maps displayed columns to native UTF-16 offsets, so Unicode fallbacks and four-cell tabs preserve correct caret, pointer and selection positions. Fallback rendering does not replace characters in source.

Code conventions

  • Use readable names, ordinary control flow, and one logical operation per line. Avoid compressing functions to save space.
  • Comment intent, data formats, invariants, and boundaries. Explain why a check or ordering rule exists; do not merely restate each assignment.
  • Keep widget appearance and behavior in Lisp. Add a native binding when the feature needs a browser service, not to move editor layout into HTML.
  • Preserve the live-edit contract: validate a candidate before replacing the working runtime or GPU pipeline. Avoid triggering input/audio/file actions during validation.
  • Use drawing scopes for temporary paint/transform changes, stable region IDs for controls, and ordered pixel composition.
  • Document new public forms in the language/API pages and include a small runnable example. 
npm run format
npm run format:check
npm test

Prettier formats JavaScript, JSON, HTML, CSS, and Markdown. Lisp is manually indented with two spaces. Unit tests use Node's built-in test runner. Add meaningful behavior tests for language, input, drawing, or synthesis changes.

Browser checks

With the local server running, execute:

node tests/browser-smoke.mjs
node tests/browser-widgets.mjs

The integration test needs Playwright and a Chromium browser. Set PLAYWRIGHT_MODULE to an installed Playwright package and BROWSER_EXECUTABLE to the browser executable if the local bundled paths do not apply. It uses a separate headless browser, not your personal browser profile.

Checks cover actual WebGPU programs, live source input and quote painting, Lisp widgets, recovery, exports, current-format persistence, documentation links, and a simulated repository subpath. Screenshots are placed in the ignored artifacts/ directory.

Host on GitHub Pages

The repository is already a static site. No runtime server or bundle step is required for hosting. Publish the repository root so both the workshop and its docs/ directory are included.

  1. Push the repository to GitHub.
  2. Open the repository's Settings → Pages.
  3. Choose Deploy from a branch, select your publishing branch, and select /(root).
  4. Keep the checked-in .nojekyll file at the publishing root.
  5. After deployment, open the site URL shown by GitHub.

A typical project URL is https://USER.github.io/REPOSITORY/. Its docs live at https://USER.github.io/REPOSITORY/docs/. Publishing only the repository's /docs folder would publish the documentation alone and omit the workshop.

All application assets and documentation links are relative to their own directory, including Lisp source fetches and the documentation action. Do not introduce root-relative /app.js or /docs/ links: those would target the user-site root rather than the project directory.

To simulate a project subpath locally, run the server with BASE_PATH=/aioli/ and optionally PORT=4174 in your shell environment. The server redirects directory URLs to a trailing slash, matching static-site directory behavior.

Publishing-source options and the .nojekyll behavior are documented in GitHub's publishing source guide and site creation guide. GitHub Pages provides HTTPS; the workshop still requires a browser/device with WebGPU support.
