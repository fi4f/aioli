Projects and tools

More files. More ways to make things.

A project contains named Lisp files, imported assets, generated images and sounds, and shared state. The file pane and tool windows are live Lisp widgets in editor/, composed from editor/ui/ controls.

File explorer

Use View → Files pane to dock the folder tree beside code and the game. Click a folder row to expand or collapse it. Nesting and expansion are saved with the project. Icons distinguish folders, code, images, audio and generic assets. Click a source to open its code tab; clicking an image or audio asset opens its preview window. Scroll vertically with the mouse wheel or vertical scrollbar; use Shift+wheel, a horizontal trackpad gesture, or the horizontal scrollbar to reveal long names and deep folders. Collapsed descendants consume no scroll space. On narrow screens, opening a source returns to the code pane.

Right-click a file, folder or empty tree area for file actions. Shift+F10 opens the selected file's menu. New file, Import resource, Download, Rename and Delete are also under File. New file and Rename open a filename dialog. Use slash-separated paths such as lib/math.lisp. New file on a folder starts inside that folder; on a file, it starts beside that file. Create starts with a commented module. Import accepts local Lisp, image and audio files under assets/ and never overwrites existing paths. Rename and drag moves update relative imports and literal paths; rejected moves preserve the working project. If evaluation fails, the working program continues while you repair the draft.

The workbench's main.lisp launches the editor; game.lisp launches the embedded application. Each receives its own module store, globals, state, input and lifecycle hooks. The editor can inspect game code and state through host APIs; the game has no access to editor state or capabilities. There is no separate editor entry. .command.lisp, .generator.lisp and .scene.lisp are editor conventions. The runtime loads modules by explicit path, regardless of extension. Folders only organize files. A new project groups the editor package in editor/ui/ and editor/icon/. Playable sample scenes live in examples/, with commands in examples/commands/ and image/audio/text recipes in examples/generators/.

Asset previews

Click an image resource to open its WebGPU preview. Drag inside the checkerboard to pan; use the mouse wheel to zoom around the pointer. The +/- controls zoom around the center; Fit resets pan/zoom and fits large images to the viewport without enlarging small ones. 1:1 displays one image pixel per screen pixel. Transparency shows through the checkerboard. Previewing never modifies the asset.

Click an audio resource to decode it with the browser's supported audio formats. The waveform preserves peaks across channels. Play/Pause resumes from the current position; Stop returns to the beginning. Click or drag the waveform to seek. The playhead and elapsed time update during playback. Closing the window, Escape, or switching to another widget stops asset playback. Preview playback is independent of procedural generator controls. A decode error appears inside the window and leaves the editor usable.

Standalone HTML export

File → Export application HTML validates the project and downloads a single HTML file. It embeds the runtime, all game source files (including dynamically selected scenes), and all assets. The editor package and editor session state are excluded. A generated main.lisp imports game.lisp, preserving project paths. Startup initializes fresh game state. Open the file directly in a WebGPU-capable browser; the exported application makes no network requests.

Inspecting the embedded application

Editor code can use (game-code "game.lisp"), (game-state), (game-get :x), (game-set! :x 160), (game-definitions), and (game-call "function-name" argument). These capabilities exist only in the editor. Commands run in the editor environment; get and set! refer to editor state. Use game-get and game-set! for the active game or scene. A single command can read and write both states without switching environments. 

; examples/commands/center-player.command.lisp
(game-set! :x 160)
(game-set! :y 190)
(game-set! :vy 0)
(set! :status "Player centered")

Import resolution

; game.lisp
(import "./lib/movement.lisp")
(defn update [dt]
  (move-player dt))
; lib/movement.lisp
(import "../lib/math.lisp")
(defn move-player [dt]
  (set! :x (+ (get :x) (twice dt))))
; lib/math.lisp
(defn twice [value] (* value 2))

import is a top-level form with one literal string. Paths resolve relative to the importing file. A leading slash resolves from the project root: (import "/lib/math.lisp"). Include the extension; there is no extension guessing, package search, or network fetch. Normalization accepts . and .. but rejects paths that escape the project, URLs and Windows paths.

Dependencies load first, once per evaluation, in import order. Missing files and cycles report the affected paths. Imported CPU definitions share one global environment; there are no namespaces or automatic exports, so choose distinct function names. Entry import graphs and discovered generators are validated on evaluation. An unused library or command file is retained in the project without being executed.

Application lifecycle hooks

; game.lisp: CPU and GPU code can share a file.
(init! :radius 20)

; Optional CPU update hook, in seconds, while unpaused.
(defn update [dt]
  (set! :radius (clamp (+ (get :radius) dt) 20 60)))

; Required render hook: compiled into a WebGPU fragment program.
(defpixel render [p time]
  (background "#101613")
  (fill "#bbd6a6")
  (circle [160 120] (param :radius)))

Without an active scene, the main import graph must define exactly one defpixel render. It can live in an imported file; the filename has no special meaning. Only this hook compiles to the scene shader. CPU forms run normally. p is the pixel position and time is elapsed game time. Pass shared state to the GPU through param. The shader subset applies inside the render hook.

Optional (defn init [] ...) runs on initial project activation, import and reset. Optional (defn reload [] ...) runs when live edits are accepted. update [dt] receives a zero-duration validation call and then a call each unpaused frame. Use top-level init! for state that should survive live edits. Optional (defn sound [] ...) produces gameplay audio; without it, audio is silent. These functions can be defined anywhere reachable from the entry points. The application CPU drawing hook is (defn draw [] ...).

Version 9 saves keep editor and application state separately. Earlier application entries move into game.lisp; old editor entries are folded into main.lisp, preserving custom code. Workspace selections follow the renamed files. Unreferenced files remain in the project without executing.

A top-level (start-scene "examples/bloom.scene.lisp") in game.lisp selects the startup scene. Changing that request during live editing switches scenes after validation, even if a different scene is saved in state. Unchanged requests preserve transitions made by gameplay or commands during unrelated edits. A missing scene or failed shader keeps the last working scene active.

Swappable scene resources

; game.lisp: application entry point
(start-scene "scenes/menu.scene.lisp")

; Later, from an update function or command:
(start-scene "scenes/level-one.scene.lisp")
; scenes/menu.scene.lisp
(init! :menu-time 0)
(defn enter [] (set! :menu-time 0))
(defn update [dt]
  (set! :menu-time (+ (get :menu-time) dt)))
(defn exit [] (set! :menu-time 0))
(defpixel render [p time]
  (background "#101613")
  (fill "#bbd6a6")
  (circle [160 120] (+ 20 (* 4 (sin time)))))

Scenes use .scene.lisp (recommended) or .scene. Paths passed to start-scene resolve from the project root. Each scene has its own function environment and imports, so scenes can reuse hook names without replacing application or editor functions. Shared project state is accessible with get/set!; choose distinct state keys or clear scene-specific state in exit. Application helpers are available in scenes; scene functions stay private to their scene.

The outgoing scene's exit [] precedes the incoming scene's init [] and enter []. An active scene's update [dt] runs after the application update, and its required defpixel render becomes the preview's WebGPU pipeline. Live edits call reload [] while retaining state. Optional scene sound [] supplies audio; otherwise application audio is used. Shader time starts at zero on scene entry. The selected scene is saved with the project.

Transitions stage state, lifecycle hooks and GPU compilation before committing. Failed transitions leave the current scene running. Browser actions requested by lifecycle hooks run after acceptance. An unselected scene file does not execute. Main may also render directly without scenes; (start-scene "") leaves the active scene and uses main's render hook. (active-scene) returns the active path or an empty string. The editor continues running across scene changes.

Generator inspectors

Open View / Generator inspector or click a .generator.lisp file anywhere in the tree. The editor discovers generators by suffix and builds controls from their state declarations. Click the selector's Next button to switch recipes. Large inspectors scroll with the mouse wheel or draggable scrollbar. Top and bottom arrows indicate hidden content. 

; tools/shapes.generator.lisp
(generator :image "Shapes")
(init! :shape-radius 48 ["Radius" 1 120 1])
(init! :shape-color "#bbd6a6" ["Color"])
(init! :shape-enabled true ["Enabled"])
(init! :shape-mode "circle" ["Mode" ["circle" "square"]])
(defpixel image [p time]
  (background "#101613")
  (fill (param :shape-color))
  (circle [160 120] (param :shape-radius)))

Numeric annotations use ["Label" min max step]; the step is optional. Bounds must be finite and increasing, the step positive, and the default within bounds. Choice annotations use ["Label" [choices...]], with a matching default. Booleans become toggles; six-digit hex colors open a color picker; other strings expose a text editor with Apply. Without annotations, literal init! values get inferred labels and controls. Computed defaults remain ordinary code and are not inferred.

Image generators declare (generator :image "Title") and provide exactly one defpixel image hook in their import graph. Their independent preview renders at 320 by 240 and time zero. Audio generators declare (generator :audio "Title") and implement (defn generate-sound [] ...) with voice calls. They expose waveform previews and a Play action. Generators can import relative or root helpers; output hooks are isolated between recipes. State is shared and persisted with the project, so use distinct state keys for independent recipes.

Keep stores PNG/WAV data in project resources. PNG/WAV also downloads it. Existing export-image and export-sound commands use the last selected generator of the matching output type. Legacy image/audio recipes migrate to .generator.lisp, with imports and workspace selections updated.

Text generators

; tools/level.generator.lisp
(generator :text "Level CSV" "levels/generated.csv")
(init! :level-name "garden" ["Level name"])
(init! :level-width 320 ["Width" 64 1024 16])
(init! :level-height 240 ["Height" 64 1024 16])
(defn generate-text []
  (str "name,width,height\n"
       (get :level-name) "," (get :level-width) "," (get :level-height) "\n"))

generate-text must return a string, including an empty string for empty output. The optional fourth declaration argument is a project-relative output filename; it defaults to generated.txt. Change it to emit CSV, JSON, Markdown, shader source, or any other text format. The filename chooses a MIME type where recognized, with UTF-8 text as the fallback. The generator formats the contents itself; choosing .json does not serialize or validate JSON.

The preview scrolls vertically with the wheel or scrollbar, with arrows for hidden lines. Shift+wheel moves sideways. Generation is cached until a declared inspector parameter changes or the source is re-evaluated. Generate forces another call, useful when reading state outside the declared fields. The editor shows runtime errors in the preview, rather than breaking gameplay.

Keep stores the exact UTF-8 text as an ordinary project resource. Download also stores it and downloads the basename. Existing resources at the same output path are replaced; source files, folder paths and paths outside the project are rejected. Outputs are limited to 6 MB, and the hook uses the interpreter's normal instruction budget. Kept text resources open read-only and are included in project JSON and standalone HTML exports.

Command palette

Open View → Command palette, or Ctrl/Cmd+Shift+P. Type part of a path to filter saved .command.lisp files in any folder, then click a result to execute it. Or type a Lisp program and press Run Lisp or Ctrl/Cmd+Enter. Palette text is transient: it is not saved as a project file and is never evaluated just because you type it. 

; A command can automate state changes and exports.
(game-set! :x 160)
(game-set! :y 190)
(game-set! :vy 0)
(export-image "assets/portrait.png")
(export-sound "assets/chime.wav")

Create a file such as tools/reset-player.command.lisp to add your own saved command. Click the small play button beside its explorer icon to run it without opening a code tab, or choose Run command from its right-click menu. Nested command folders work too. These programs run explicitly rather than during normal live evaluation. Commands share editor CPU definitions and state and can import helpers relative to their own directory. Typed palette programs resolve imports from the project root. Use get/set! for editor state and game-get/game-set! for game/scene state, or reset-project to rebuild all state from defaults.

Each loaded module uses the normal evaluation budget. Execution is sequential: effects before an error remain. Browser file/audio actions are deferred until the command finishes its synchronous forms, and report errors in the status bar. Drawing primitives belong inside editor or pixel hooks; commands should call services and change state.

Keeping the current editor

Unmodified bundled editor components upgrade automatically when a saved project loads. Customized components keep their source; use the recovery shell to adopt the latest widgets.

F2 opens the latest recovery shell without replacing your project’s editor source. Creating or renaming files, editing gameplay or generators, and resetting state keep that shell active, including after reload. Accepting an edit to main.lisp or editor/ui/components.lisp returns to the project editor.

In recovery, Use latest editor adopts the bundled editor and widget library permanently. Changed project sources are kept as editor-backup-1.lisp and ui-backup-1.lisp (with increasing numbers if needed). The control appears in Project on every screen. View → Project editor explicitly leaves recovery without upgrading.

Custom editors can use (recovery?), (upgrade-editor), and (leave-recovery). Recovery mode is saved with the project, while recognized unmodified stock source is upgraded by content even if the project already uses version 3.

File pane APIs

(project-tree) returns up to 64 visible rows beginning at the clamped :file-offset. Each row is [path kind buffer-key basename depth expanded asset-kind]. Kind is folder, lisp or asset; asset-kind is folder, code, image, audio or asset. MIME metadata and filename extensions identify imported assets. (project-tree-count) counts visible rows and (project-tree-offset) returns the viewport-clamped offset. (toggle-folder path) changes expansion and resets scrolling; expansion is a JSON string in :open-folders. Set :show-files to toggle the pane.

(resource-region path kind asset-kind origin size) registers a tree row for pointer, keyboard and context menu input. Icons, nesting, scrolling and menus are painted by Lisp. Filename dialogs use :window "file-path" and the transient __path buffer. Names beginning with __ are reserved for input buffers.

Project format and persistence

Version 21 JSON has files (named source strings), resources (MIME type and base64 data URL per asset), editor state, separate applicationState, and an optional recovery flag. Source drafts are included in a manual Save project; automatic browser persistence retains accepted source. Resource changes are saved with the project. v1/v2 saves migrate without losing custom source or state; stock editor/widget definitions receive the new tools. F2 opens the latest recovery shell if a custom editor has no controls for them.

Limits are 256 source files, 100,000 characters per source, 256 assets, and 6 MB per imported/generated asset; project imports allow 16 MB total. Browser-local storage has its own quota. If a large project exceeds it, use Save project to preserve it as JSON. Two entry names, main.lisp and game.lisp, are fixed; additional files are unlimited in role within the stated file count. All source and assets are project data, so GitHub Pages hosting still requires only static repository files.
